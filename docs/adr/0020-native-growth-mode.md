# ADR-0020：原生增长模式（嫁接式）

- 状态：已接受
- 日期：2026-10-10

## 背景

ADR-0017 把写盘落到原生 MMC 命令，ADR-0018 把读盘落到 MMC 读块加 ISO 9660 解析，
Windows 上只剩“把目录追加到已有盘”没有原生实现：`optiburn_engine::grow` 在
Windows 仍走 xorriso，而 Windows 上没有能访问光驱的 xorriso 构建（ADR-0008 补记），
于是 GUI 的追加页与 CLI 的 `append` 在 Windows 上报“缺 xorriso”。缺口的具体形状是
把新目录并进盘上末区段：旧文件必须继续可见（Windows 只挂载最后一区段），但旧文件的
数据不该重写一遍。

两个前置条件已经具备：原生读侧能读出末区段的 Joliet 目录树（ADR-0018），原生写侧能
从任意 NWA 往后写新区段（ADR-0017）。

## 决策

1. 增长用“嫁接式”：只写目录结构与新文件数据，旧文件的数据块原地引用，既不重读也
   不重写。生成器（`crates/optiburn-engine/src/grow.rs`）按合并后的目录树现算一张
   ISO 9660 + Joliet 会话镜像，再交给既有写序列按块下发，写盘路径与镜像刻录完全共用
   （`native::write_image`）。
2. 会话内所有地址写盘级绝对地址：目录记录、路径表、描述符里的根目录记录与路径表
   位置一律是“区段起点加会话内相对块号”。只有描述符里的卷空间大小是区段相对值。
   依据是标准读取器的行为：Linux 内核 isofs 从 `s_firstdatazone` 起把目录记录里的
   extent 直接当盘上块号用，不经任何偏移。libisofs 的 `ms_block` 语义把镜像内全部
   引用都加上基址，卷空间大小写镜像自身大小。ADR-0018 在 xorriso 增长的区段上实测到
   同一形状（起点 150093 的区段，根 extent 150112 是绝对地址，vss 107575 是相对值）。
   自家镜像刻录路径（起点 0）两种约定重合，因此生成器对所有调用点都写绝对地址。
3. 会话形状只写 ISO 9660 与 Joliet 两个命名空间，不写 UDF。追加不改变盘上原有 UDF
   分区的内容，新区段的卷识别序列也不再提供 UDF 描述符：按最后一区段挂载的读取器
   （Windows）看到的是新会话的 ISO/Joliet 树，与 Linux 内核按区段起点挂载的结果一致。
   代价是 Windows 上 UDF 优先的读取路径在追加后落到 ISO 9660 上，长文件名与中文名
   仍由 Joliet 提供（同 ADR-0006 的取舍）。写进字节布局的规则：
   - 块 0 到 15 系统区全零，块 16 PVD、17 Joliet SVD、18 终止符。
   - 块 19 起四张路径表：PVD 的 L 表、PVD 的 M 表、Joliet 的 L 表、Joliet 的 M 表，
     各占整数块。路径表记录按 ECMA-119 9.4：长度、扩展属性长度 0、extent 四字节、
     父目录号两字节、标识符，标识符长度为奇数时补一个 0 字节（记录总长恒为偶数）。
   - 之后是主命名空间的目录数据（根目录先，再按路径表顺序），然后是 Joliet 的目录
     数据，最后是新文件数据（按主命名空间的目录顺序，同目录内按 Joliet 标识符字节序）。
   - 目录记录用上游 `hadris_iso::sync::directory::DirectoryRecord::new` 生成：`.` 与
     `..` 为自引用记录，子目录在前、普通文件在后，各组按本命名空间标识符的字节序。
     旧文件保留盘上原有的时间戳，新文件用当前时间。
   - 命名转换用上游实现（与 `build_image` 的镜像一致）：Joliet 走 UTF-16BE、最多 64
     个码元，BMP 之外的字符替换为 `_`。主命名空间走 Level 2 大写名，文件追加 `;1`，
     目录不加版本后缀。
   - 零长度的新文件不占数据块，其 extent 会落在文件数据之后，因此布局在有零长度新文件
     时给会话末尾补一块零块，让每个 extent 都落在卷内。
4. 合并语义按目录逐层进行：同名新文件替换旧条目（旧数据不再被引用），同名新目录与旧
   目录递归合并。新文件与旧目录同名（或反过来）报 `GrowConflict`。合并后每个目录里
   Joliet 标识符与主命名空间标识符都必须各自唯一，冲突报 `GrowConflict`（主命名空间的
   截断与替换规则会把不同名字映射到同一个标识符，中文名尤其容易撞上）。源目录里
   符号链接与特殊文件跳过，与 `build_image` 的 `FileTree::from_fs` 一致。源目录一个
   文件都没有时报 `NativeGap::EmptyGrowSource`。
5. 读旧区段用原生读侧同一套地址约定判定：描述符区永远在区段起点加偏移，目录记录里的
   extent 按“根目录首记录是否自引用”探测是区段相对还是盘级绝对。旧区段的起点取
   `READ TOC Format 1` 报的末区段起始地址，不取 NWA：NWA 是下一个可写地址，位于旧
   区段之后，用它定位旧区段会读到空白（或读到即将覆盖的位置）。写新会话用 NWA 作
   区段起点。
6. 旧区段的形状限制一律显式报错，不静默降级：没有 Joliet 目录树、含启动记录、含多
   extent 文件（记录 flags 的 0x80 位）、目录嵌套超过 8 层、目录树有环、目录数据超过
   64 MiB、记录越过块边界或目录数据末尾、非空文件落在空 extent、符号链接的 SUSP 条目
   （`SL`）出现在读到的记录里，都归 `GrowUnsupported` 或 `ReadFailed`。
7. 容量门禁在引擎内也做一次（`BurnError::NotEnoughSpace { needed, free }`）：会话尺寸
   要等生成计划算完才准确（目录结构、路径表、补位都要算进来），调用方的写前预演
   （ADR-0019）用同一个尺寸口径。口径取 `MmcDevice::read_disc_capacity` 的可用容量，
   读不到就跳过，由驱动器的写错误兜底。
8. 随机可写介质（DVD-RAM、BD-RE，盘片状态位 0b11）不支持增长，报
   `NativeGap::GrowthOnRewritable`：这类盘可以直接整体覆写，不必嫁接。已封口的盘报
   `NativeGap::FinalizedDisc`。
9. 平台分派与读写侧同规则：Windows 走原生增长（ADR-0017/0018 已在那边实机验证），
   Linux 维持 xorriso 增长模式（ADR-0006）。`optiburn_engine::grow_size` 也分派：
   Linux 仍是 `xorriso -print_size` 预演，Windows 用原生会话计划的字节数。

## 后果

- Windows 上 `append` 与 GUI 追加页不再依赖外部程序：追加的写前门禁、容量预演、会话
  生成、写盘全部在进程内完成。GUI 追加页的完成通知仍按老办法重开设备读一次区段数。
- 追加只占盘的增量空间：新区段是目录结构加新文件，旧文件不重写。实测的会话开销与
  `SESSION_OVERHEAD` 的 16 MB 余量没有冲突（区段 lead-in/lead-out 由门禁余量兜）。
- 同一条 `native::write_image` 服务镜像刻录与会话写入，两条路的进度回调、取消粒度、
  末块补零一致。
- 只写 ISO/Joliet 的取舍要在读侧保持自洽：Windows 上追加过的盘，其末区段不再有 UDF
  描述符，读取走 ISO 9660（ADR-0018/0021 都能读）。
- 已知边界（本轮不处理，写在这里避免下一个人重踩）：
  - 旧区段里的 Rock Ridge 元数据不结转：新会话只提供 Joliet 名与派生的主命名空间名，
    旧条目的 RRIP 权限与符号链接信息丢失。符号链接若只在主命名空间的记录里带 `SL`，
    读 Joliet 树时看不出来，会当作普通文件（通常长度 0）保留。
  - 旧区段若是 xorriso 增长出来的区段（绝对地址约定），读侧能正确解析（ADR-0018 探测），
    但那些区段的 RRIP 名不参与，名字一律以 Joliet 树为准。
  - 非 CD 介质上 `READ TOC Format 1` 可能回 track 1、LBA 0 的假值（MMC-5 6.26.3.3.3），
    此时读旧区段会定位到错误位置并报 `NoIsoSession`（读侧同一处缺口，ADR-0018 已记）。
    追加门禁在写前先跑 `last_session_is_iso`，同一条 TOC 路径已经把这类盘拦在前面。
  - 目录内标识符唯一性是硬性约束：主命名空间里两个中文名替换后相同（都变成下划线）
    会被拒绝，即使 Joliet 名字并不相同。

## 被否决的方案

- 重建式增长（把旧文件读出来，重新生成一张完整镜像再写）：读盘一遍、写盘一遍，
  占盘空间与耗时都等于整盘重刻，且慢速介质上读回旧数据的失败风险高。
- 用 `hadris_iso::modify` 的 `IsoModifier` 追加：它把新会话写回同一镜像文件，会回写
  扇区 16 的卷描述符，且上游的修改路径按单一命名空间处理，Joliet 名会丢。
- 先写区段相对地址的会话，再在字节上做整体位移补丁：位移要改目录记录、路径表、两份
  描述符的根记录与路径表位置，等于把生成时的地址算术再做一遍，还不如生成时直接写
  绝对地址。ADR-0018 的“写侧位移补丁”缺口因此关闭。
- 生成时把旧文件数据也复制进新区段（自包含会话）：等于重建式，只是省了读回的一步。

## 补记：真机实测（2026-10-10，Windows，USB 光驱 D:，可追加 CD-R）

- 追加测试（`native_grow_and_read_back_real`）：盘上原有 24 个条目，追加两个小文件
  （一个 ASCII 名、一个中文名）到卷标 `GROWTV1` 后读回 26 个条目，旧路径集合是新
  集合的子集，两个新文件逐字节一致，卷标是新区段的卷标。写盘前的路由读到了旧区段
  （READ TOC Format 1 报末区段起点 286770），新区段从 NWA 起写，卷空间 31 块。
- 旧区段的数据块确实被原地引用：测试断言新区段的字节里不出现旧文件的内容，而读回
  时旧文件内容正确（说明记录指回旧块）。
- 观察到的写序列与镜像刻录一致（就绪、读盘片信息、读 Profile、读剩余容量、写参数、
  WRITE(10) 若干、SYNCHRONIZE CACHE、CLOSE TRACK/SESSION），因此两条路共用同一条
  写函数没有代价。
- 结构层面的对拍：生成器的单元测试用 mastering 造的旧区段（含中文名、空文件与两级
  目录）与读侧互为对拍，另外用独立的手工字节解析核对根记录与文件记录的 extent 是
  盘级绝对地址、卷空间是区段相对值、路径表大小与四张表的实际字节数一致。
- 独立读取器判据（2026-10-11，Linux 6.8 主机）：把真机写下的那个会话（起点 286770，
  31 块）从盘上读出来，补齐 286770 块零前缀后交给标准读取器：
  - 内核 isofs：`mount -t iso9660 -o loop,ro,sbsector=286770` 成功，列出的路径集合与
    原生读侧一致（旧文件加两个新文件），中文名正确，旧文件的大小与时间戳保留，两个
    新文件的内容 md5 与本地源文件相等。
  - xorriso 1.5.6：`-indev <镜像> -load sbsector 286770 -pvd_info` 报
    `Volume Id : GROWTV1`、`PVD address : 286786s`（起点加 16），加载镜像树时读到
    26 个节点，与原生读侧一致。
  这两条是“绝对地址约定能被标准读取器读”的直接证据。
- Windows 挂载视图（2026-10-11，同一台机器，把光盘弹出再放回后）：`Get-Volume
  -DriveLetter D` 报 `FileSystemLabel : GROWTV1` 与 `FileSystem : CDFS`，也就是新会话
  的卷标；资源管理器递归列出 26 个条目（旧树 24 个加追加的两个文件），中文名正确，
  两个追加文件的 md5 与本地源文件一致，旧文件（ARCHITECTURE.md 8376 字节、
  WINDOWS-COMPAT.md 5768 字节）的 md5 与原生读侧抽出的字节逐个相等。Windows 只按
  末区段起点加偏移把 extent 当盘上块号读，这条是绝对地址约定在目标平台上的直接证据。
  托盘需要手动推回：这台 GP70N 忽略 SCSI 的 Load 命令（`START STOP UNIT` 的
  LoEj=1/Start=0、Immed 变体、`PREVENT ALLOW MEDIUM REMOVAL` 都试过）。

## 补记：与当初实施计划的偏离

实施计划里有两处与 ECMA-119 或设备语义不符，按证据改正：

- 路径表记录的补位规则是“标识符长度为奇数时补一个 0 字节”（记录总长恒为偶数），
  不是“偶数时补”。依据是 hadris-iso 的读写两侧（`PathTableEntry::size` 是
  `(8 + len + 1) & !1`，写入时 `len % 2 == 1` 才补）与 hadris-iso 自身布局测试
  （只有根目录时的路径表大小是 10）。本仓库按 hadris 的口径写，读侧也用它的解析。
- 追加时旧区段的起点必须用 `READ TOC Format 1`，不能用 NWA：NWA 是下一个可写地址，
  旧区段在它前面。ADR-0018 的实测已经记下这一点（末区段起点与 NWA 是两个值）。
