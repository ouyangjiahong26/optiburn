# ADR-0006：默认多区段，追加走增长模式

- 状态：已接受
- 日期：2026-10-08

## 背景

CD-R/DVD-R 写完就封口的话，盘不能再加内容。用户要求默认不封盘、能多次刻录，且这些
处置由软件自动完成，不留给操作者判断。

封口与否由 `-multi` 控制（ADR-0004 的参数表）。真正难的是追加：hadris-cd 只能从零建
整盘镜像，没有 mkisofs `-C`/`-M` 式的区段续写。把第二份独立镜像直接写上去，Windows
（默认挂载最后一个区段）就只能看到新文件，旧文件像被删掉一样。本地检查 hadris-iso
2.5.0 源码确认它没有区段偏移或续写 API。

## 决策

1. `burn` 默认带 `-multi`（不封口），`--close-disc` 显式封盘。
2. 追加一律走 xorriso 增长模式：`xorriso -dev <设备> [-speed N] -volid <卷标>
   -joliet on -map <目录> / -commit`。`-dev` 会读出盘上已有区段的目录树，新区段同时
   携带新旧文件，旧文件保持可见。空盘时它直接写第一区段，所以 `append` 不必区分
   首刻与追加。`-map <目录> /` 把目录内容映射到盘根，与 `build-image` 的语义一致。
   结束盘的生命周期用 `append --close-disc`，提交前加 `-close on` 把盘标记为不可
   追加。`burn --close-disc` 只对空盘有意义，因为可追加盘走镜像路径已被前置检查
   拒绝。`-close on` 对随机可写介质不生效（xorriso 手册明示），这类盘无需封盘即可
   覆写。
3. `burn` 与 `append` 共用前置检查（CLI 的 `ensure_burnable`）：先按 `TEST UNIT
   READY` 等介质就绪（20 秒内每 500 ms 重试），再按 `READ DISC INFORMATION` 路由：
   空盘放行，已封口拒绝，可追加盘拒绝走镜像路径并提示改用 `append`（防止上面的
   遮蔽事故），随机可写介质（状态位 0b11，例如 DVD-RAM、BD-RE）直接放行（无遮蔽
   问题），只有 `append` 自己放行可追加盘。检查完立刻释放设备句柄，再交给引擎
   独占打开。

## 后果

- 多次刻录成为默认行为且有实机验证：在 `/dev/sr0`（ThinkPad Ultraslim DVD，空白
  CD-R）先 `burn` 镜像再 `append` 目录，回读目录树两批文件都在，第一次写入的内容与
  源文件 `cmp` 逐字节一致。
- 区段合并依赖 xorriso 的目录树模型。`build-image` 产出的独立镜像文件不参与合并，
  追加的输入是目录（`append`），不是镜像。
- 前置检查只需要读侧命令，放在 CLI 而不是引擎里：引擎的输入已经是一个确定的任务，
  按介质状态路由是命令行的事。
- Windows 侧未验证：设备枚举还没实现（ADR-0005），`append` 在 Windows 上的行为等
  有硬件再确认。

## 补记：Windows 现状（2026-10-10）

本文说「Windows 侧未验证：设备枚举还没实现」：枚举与 probe 已真机验证，原生 MMC 写
引擎也已落地（ADR-0017），刻录在 Windows 上走它。仍未验证的是 `append`：增长模式
只有 xorriso 一条路，Windows 上没有可用的 xorriso 构建，多区段追加在那边的行为也还
没有真机确认。

## 补记：Windows 的 append 已经可用（2026-10-11）

原生增长模式已落地（ADR-0020）：Windows 上 `append` 与 GUI 追加页不再依赖 xorriso，
读出末区段的 Joliet 目录树，生成只含目录结构与新文件数据的新区段，旧文件数据原地
引用，已在 CD-R 上真机追加并读回对拍。本文的决策 2（追加一律走 xorriso 增长模式）
在 Linux 上不变，Windows 上由原生实现承担同一件事；决策 3 的前置检查（按盘片状态
路由、末区段必须是 ISO 9660）两端一致。
