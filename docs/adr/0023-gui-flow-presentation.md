# ADR-0023：界面里的流程呈现（SOP）

## 背景

界面要回答的不是“有哪些功能”，而是“用户拿到这张盘，下一步该点哪里”。上一轮把抢救这条特例连同整段说明铺在设备页首屏的文件清单上方，反馈是“放这里有些丑陋”：主流程被特例挤占，用户在还没做出选择之前就被迫读一段长文。这份约定把当时的判断写成规则，供后续界面改动照做。

## 决策

1. 主流程占结构。四个页面对应四条命令（读盘、追加、刻录、制作镜像），页面首行一句话说清这一页干什么。
2. 字段级提示就地给。输入旁边的说明写默认值与后果（“留空交给驱动器自选”“封盘后不能再追加”），不写进页面级长文。
3. 特例不抢主位。抢救、修复、回退确认这类只在条件成立时出现，入口一行。详细说明放在执行那一刻的确认框里，首屏不铺文字。
4. 结果与错误必须给下一步。完成消息说清发生了什么与下一步做什么，错误按成因归类并给可执行动作。
5. 跨页动作在结果里指路。抢救没有可救内容时，结果里说明另一种中断形态按普通读盘取，或追加时确认跳过残片。
6. 顺序规则写在使用它的地方。先抢救后修复，写在抢救的确认框与 `repair` 的说明里，不写进首页长文。
7. 界面与文档同一套词，用 CONTEXT.md 的术语（抢救、未关闭轨道、末区段），FAQ 的处置流程与界面提示逐条对应。

## 后果

- 抢救入口是设备卡片展开后的一行按钮，说明在确认框里（本次改动）。同类特例（修复、回退确认）沿用同一形状。
- 用户可见的处置流程只有两处：界面在触发点给一句话加确认框，FAQ 给完整顺序（六步）。两处逐条对应，术语一致。

## 被否决的方案

- 把特例的完整说明铺在首屏：主流程被挤占，用户在未做选择前被迫读长文（本次反馈）。
- 特例藏进别的页面或设置项：触发时找不到入口，等于没有这个功能。
- 界面里的说明与文档各写一套：两处措辞与顺序会漂移，用户按任一处做都可能出错。
